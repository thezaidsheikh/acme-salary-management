# Trade-offs

| Decision | Chosen | Why | Alternative + why not |
|---|---|---|---|
| DB | PostgreSQL 16 | Relational, correct for salary + audit; indexes, transactions, aggregates. The brief asks for a relational DB. | SQLite — zero-setup, but no concurrent writes, weaker types; only a local fallback, never the design target. MongoDB — wrong shape for joins/audit. |
| Backend | Express + TypeScript | Light, familiar, fast to build well; layered code keeps it maintainable. | NestJS — more structure out of the box, but heavier boilerplate for this size; Express + strict layering gives the same discipline with less ceremony. |
| Architecture | Modular monolith | One deployable, clear module boundaries (employees / salary / analytics / bands + shared kernel); each module can be extracted into a microservice later without a rewrite. | Microservices now — distributed transactions, deployment and debugging overhead for a 10k-employee HR tool; the brief says "not the most complex system, good judgment". Layered monolith without module boundaries — cheaper today, but extraction later would be a rewrite. |
| ORM / DB driver | `pg` (node-postgres) + plain SQL migration | No binary downloads, standard driver, full SQL control; the repository interface means swapping back to Prisma later is a one-file change. | Prisma — first choice, but its engine binaries download from `binaries.prisma.sh`, which is unreachable from this VM (verified: curl returns Cloudflare 404, `prisma generate` fails with ECONNRESET). Kept the same schema, indexes and interface, so nothing else in the app changed. |
| Frontend | Next.js 14 (App Router) + React 18 + Tailwind 3 | The assessment allows ReactJS or NextJS and the user chose Next.js: file-based routing, layouts, metadata and production conventions in one framework; pages are client components fetching dynamic HR data at runtime. | Vite SPA — faster dev start and a smaller build, but no file routing/layouts and the assessment's NextJS option was explicitly chosen by the user. Rejected in the rework for that reason, not for a technical failure. |
| Pagination | Server-side, default 20, max 100 | 10,000 rows must never hit the browser at once. | Client-side — simple but slow and memory-heavy at 10k. |
| Salary storage | Current salary on Employee + SalaryHistory audit | Fast reads for list/dashboard; history is the audit truth. | History-only (compute current from latest) — correct but slower for every list row. |
| Analytics | Grouped SQL + in-memory median/buckets | Medians need sorted values; aggregates are small, so this is fast and exact. | Precomputed materialised views — faster at 1M+ rows, overkill at 10k. |
| Charts | Plain tables + CSS bars | Deterministic, no extra dependency, accessible. | Chart lib — prettier, heavier; not needed to answer the pay questions. |
| Auth | None (documented out of scope) | Single HR persona in the brief; focus the effort on the core. | JWT/RBAC — would be the next step before real production use. |
| Salary bands | `salary_bands` table (one row per level, monthly USD min–mid–max), seeded by migration 002 | Bands are HR data, not code: they change when pay policy changes, and a deploy should not be needed to change them. The table is the single source of truth — the seed generates salaries from the same values (`LEVEL_BANDS_USD`) and the API reads the table, so the two can never drift apart. One row per level also makes a future admin UI trivial (UPDATE one row). | Hard-coded in the seed / a config file — simpler to start, but the numbers would live in code: every band change needs a deploy, and the seed's bands and the API's bands would be two copies that can disagree silently. A per-employee band column — wrong shape: the band belongs to the level, not the person, and duplicating it 10,000 times invites inconsistency. |
| Compa-ratio currency | Fixed FX rates — the same rates the seed used (`shared/analytics.ts`: INR 83, GBP 0.79, EUR 0.92, SGD 1.34, CAD 1.36, AUD 1.52, AED 3.67 per USD) | The seed generates salaries as `USD band × FX × country factor`, so converting back with the same fixed rates compares like for like: a salary generated from a band converts back into that band (a Senior in India at the band minimum converts to exactly the band minimum in USD). Fixed rates are deterministic and testable — the same employee always gets the same compa-ratio — and the assessment already rules out live FX (non-deterministic, needs an external source). Payroll itself is never converted: it is stored and paid in local currency; USD exists only for comparison, and the UI says so. | Live FX rates — accurate to the day, but the ratio would change every day for the same salary, tests could not assert exact values, and the app would need an external FX source (a new failure mode). Comparing in local currency — meaningless across levels: a band is defined in USD, so the salary must be converted into USD to be compared with it. |
| CSV upload | multer 2.5.0 (pinned) + `@types/multer` 2.3.0, memory storage, 5 MB cap, `.csv` filename required | One well-known dependency for the one hard part (multipart parsing); memory storage means no temp files to clean up and nothing written to disk, and the 5 MB cap bounds the memory. Multer 2.x, not 1.x: the 1.x line is deprecated with unpatched vulnerabilities, and 2.x is the maintained line. | A hand-rolled multipart parser — the boundary format is fiddly and a bug would be a security hole; `busboy` directly — multer is the standard wrapper over it, and the app needs nothing busboy adds. `express.json()` cannot parse multipart at all. |
| CSV parsing | A ~70-line RFC 4180 parser in the employees module (`employee.csv.ts`) | The whole problem is quoted commas, doubled quotes, CRLF and blank lines; a library would be a dependency for 70 solved lines, and the parser is fully branch-covered by tests. | `csv-parse` / `papaparse` — correct, but a second dependency for a small, testable function; papaparse is also a browser-first library. A regex split on commas — wrong the first time a job title contains a comma (the test file has one: "Engineer, Platform"). |
| Import transaction | One multi-row INSERT statement (single implicit transaction) | All valid rows commit together or none do — one statement is atomic by definition, so there is no explicit BEGIN/COMMIT to manage and no client checkout; the service pre-checks duplicates (`existingEmails`) so the statement never hits a unique violation mid-batch in normal use. Verified: a duplicate mid-batch inserts nothing (Pg pg-mem + InMemory tests). | Row-by-row inserts in an explicit transaction — same outcome, but N round-trips and a checked-out client to release; a loop without a transaction — a failure halfway would leave a partial import, which is exactly the silent state the report must never hide. |
| Import header | Must match the export columns exactly, in order (`EMPLOYEE_CSV_COLUMNS`, one shared constant) | Export and import can never drift apart, and an exported file round-trips unchanged — HR's most likely first import is the file the app itself exported. A wrong header is a 400 with the expected header in the message, so the fix is obvious. | Accepting any column order / extra columns — friendlier, but silently guessing which column is which is how salary data lands in the wrong field; a mapping UI is a whole feature for a problem the export already solves. |
| Duplicate emails | Reported as failed rows (in-file duplicate, or already stored), never a crash | The import's contract is per-row reporting: a duplicate is a data problem in one row, not a reason to fail the other 9,999. The service checks duplicates before inserting, so the bulk insert never aborts on them. | `ON CONFLICT DO NOTHING` in the INSERT — would silently drop the row, and the report could not tell HR *why* it was skipped; failing the whole import on one duplicate — punishes the good rows for one bad one. |
| Upload size limit | 5 MB (multer `limits.fileSize`) | ~45,000 rows per file at ~110 bytes a row — far above a single HR spreadsheet — while bounding memory (the file is held in RAM) and request time. A bigger file is a 400, not a crash. | No limit — an unbounded upload is a trivial denial-of-service on a free-tier service; a 1 MB limit — too small for a real migration file (10,000 rows is ~1.1 MB). |
| Imported `id` column | Accepted, ignored — the repository assigns fresh ids | An exported file round-trips without editing, and an import can never collide with (or overwrite) existing rows by reusing their ids. Imported employees have no manager (`managerId` is not an export column) until one is set afterwards. | Honouring the CSV's ids — would let a file overwrite existing employees by id, which is a silent data-loss path; rejecting files that contain an `id` column — would break the export → import round-trip. |

## What I would improve next (honest)
1. Auth + RBAC (HR admin vs viewer) and `changedBy` from the real user.
2. Salary-change approval flow for large increases.
3. Materialised analytics + caching if headcount grows past ~100k.
4. A small admin UI for editing the `salary_bands` rows (the table exists; HR currently changes bands directly in the database).
